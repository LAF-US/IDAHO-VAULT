# Fleet Report — Soulslike & Roguelike: the Death Economy and the Run/Meta Split

*Filed 2026-07-04 by the mechanics research fleet for Logan's review, completing issue #754's third item. Draft only. I propose; Logan inscribes.*

![[PROVENANCE-MARKS]]

**Scope note.** Phoenix's sibling report (`!-REPORT-MECHANIC-CHECKPOINT-RESPAWN-2026-07-04.md`) already covers the recovery CONTRACT — checkpoint restore semantics, the one-shot bloodstain/rune reclaim, `keepInventory`-style axes. This report does not re-derive those mechanics. Its subject is the **death economy**: what a death costs, what a death teaches, and which class of state is designed to outlive the run that produced it.

## The Mechanic (as it actually works)

**Dark Souls: the souls economy and the designed floor of loss.** Souls are the single currency for both leveling and buying goods. On death, 100% of carried souls drop at the death location as a bloodstain; the run to retrieve them is the one-reclaim window Phoenix's report already specifies [verified: http://darksouls3.wikidot.com/game-mechanics-general]. What the economy defines as *never at risk*, regardless of how many times the player dies: character level (souls already spent leveling up), all equipment and upgrades already applied to that equipment, and every bonfire already lit (the checkpoint network is permanent once discovered) [verified: http://darksouls3.wikidot.com/game-mechanics-general; https://darksouls.fandom.com/wiki/Hollowing]. Only *unspent, uncollected* currency is disposable. Layered on top is Hollowing: repeated death while carrying a Dark Sigil accumulates a curse stat (capped at 99, cosmetic-visible at 15) that is reversible only by deliberate, costly action (a Fire Keeper Soul plus souls equal to several level-ups, or a Purging Stone) [verified: https://darksouls3.wiki.fextralife.com/Hollowing]. Hollowing is notable precisely because it is a death-cost with no reclaim mechanic at all — a pure tax on repeated failure that exists alongside the recoverable souls tax.

**Rogue / NetHack: permadeath as the founding rule, not a difficulty option.** Rogue's creators tested a save-and-resume feature and found players reloading saves to re-roll bad outcomes — "save-scumming" avant la lettre. Their fix defined the genre: the save file is deleted the instant it is loaded, so a character's death is architecturally unrecoverable, not merely discouraged [verified: https://en.wikipedia.org/wiki/Rogue_(computer_game)]. Designer Michael Toy called the goal "consequence persistence" — forcing the player to focus on avoiding the character's death *at that moment* rather than memorizing a solution sequence [verified: https://en.wikipedia.org/wiki/Rogue_(computer_game)]. NetHack's one cross-run artifact is the **bones file**: a snapshot of a dungeon level as it existed at the moment a character died there, with a probabilistic chance (rising with depth) of being loaded into a *different* future game in place of a freshly generated level — carrying over that dead character's remains, dropped items, and any monsters that spawned from the corpse [verified: https://nethackwiki.com/wiki/Bones_file]. A bones file transmits only environmental residue, never player skill, currency, or character state; the genre's own community formalized this line in 2008 as the "Berlin Interpretation" distinguishing games with permadeath-and-no-reward-for-winning ("roguelike") from games layering unlocks on top ("roguelite") [verified: https://en.wikipedia.org/wiki/Roguelike].

**Hades: the two-currency split, made visible before the player commits.** Hades sorts every reward into exactly two classes, and signals the class on the door *before* the room is entered: a blue laurel wreath around the door icon marks a persistent Artifact (Darkness, Gemstones, Chthonic Keys, Nectar) that survives death and is spent between runs; a gold/yellow laurel wreath marks a run-bound resource (Obols, Boons, Centaur Hearts, Daedalus Hammer upgrades) that is wiped at death or at successful escape [verified: https://gamerant.com/hades-door-symbol-guide/; https://hades.fandom.com/wiki/Chambers_and_Encounters]. Darkness is spent exclusively at the Mirror of Night, a fixed meta-progression ledger of permanent talent unlocks reached only between runs, in the hub [verified: https://www.gamepressure.com/hades/charons-obol-nectar-and-darkness/z6d9c6]. The player never has to guess which reward class they are about to pick up — the icon plus wreath color is the interface contract, decided at design time, not inferred after the fact.

**Slay the Spire / FTL: the unlock/seed boundary.** Both games generate a run's terrain — map layout, encounters, item pool order — from a seed fixed at the start of that run; the same seed reproduces the identical map deterministically, but a fresh run gets a fresh seed [verified: https://slaythespire.wiki.gg/wiki/Map_Generation]. What survives a run's failure is disjoint from what the seed controls: Slay the Spire unlocks new cards/relics into the *available pool* for future runs (never handed to the player mid-run, never altering the current seed's map) [verified: https://cjleo.com/blog/on-slay-the-spire-and-making-games-more-loser-friendly/]; FTL unlocks new starting ships and ship layouts, and nothing else — no stat, item, or currency carries forward, which is exactly why FTL is cited as the harder edge case for the roguelike/roguelite line [verified: https://ftl.fandom.com/wiki/Ship; https://steamcommunity.com/app/212680/discussions/0/4753074843854773421/]. In both, the unlock changes *what a future run can draw from*, never *what the current run already drew*.

**Design theory: stakes produce attention; difficulty is trust.** Permadeath's designed function is to make every decision in a run carry weight it would not carry if reloadable — Andrew Doull's analysis frames it as the one feature that separates the roguelike genre from "a world of quick saves and regenerating health" [verified: https://www.gamedeveloper.com/game-platforms/analysis-the-game-design-lessons-of-permadeath]. Dark Souls extends this into a *trust* claim: the game withholds a map, a quest log, and most explanatory text, forcing players to build working knowledge from repeated, costly failure and from community-transmitted lore — the design bet being that obscured information plus real stakes produces deeper engagement than guided, low-stakes onboarding [verified: https://www.gamedeveloper.com/design/extended-fiction-in-game-design-dark-souls].

## The Problem It Solved

A system with no death cost cannot teach, because nothing distinguishes a good decision from a lucky one — outcomes are reversible on demand, so the player has no reason to build a model of *why* an attempt failed. Rogue's founders discovered this directly: with reloadable saves, players optimized around the save file, not around the dungeon. Deleting the save on reload was not a punishment; it was the fix that made "the run" a meaningful unit of measurement again [verified: https://en.wikipedia.org/wiki/Rogue_(computer_game)]. Death-with-cost forces retrospective analysis — what killed me, what will I do differently — and each of the five systems above answers a follow-on question the pure Rogue answer leaves open: *if literally nothing survives a run, does years of practice count for anything?* Dark Souls answers with the level/gear/bonfire floor: mechanical mastery survives even when a given attempt's disposable currency does not. Hades and the roguelites answer with meta-progression: a currency class explicitly walled off from run failure, spent on a ledger the run itself cannot touch. NetHack's bones files answer partially and asymmetrically: the *world* remembers a death (as terrain), the *player* does not inherit any of the dead character's power.

## Constraints & Failure Modes

- **Save-scumming.** The generic exploit against any permadeath system: copy the save file before a risky action, restore it if the action fails. NetHack's own wiki documents the method and treats it as cheating against the design; the genre-wide fix, inherited from Rogue, is architectural — delete or overwrite the save the instant it is loaded, so there is no file left to copy back [verified: https://nethackwiki.com/wiki/Save_scumming; https://en.wikipedia.org/wiki/Ironman_(computer_gaming)]. Turn-based tactics designers report the same countermeasure by another route: give the player a bounded, in-fiction recovery path (retrieve the corpse) so reloading has no upside the design didn't already offer honestly [verified: https://discussions.unity.com/t/our-design-idea-for-preventing-savescumming-in-our-turn-based-tactics-game/519259].
- **Progression laundering (meta-currency substituting for skill).** When meta-progression raises the *floor* a player operates from — more starting health, cheaper upgrades, a wider unlock pool — the player's improved win rate becomes causally ambiguous: did skill improve, or did the floor simply rise underneath unchanged skill? A comparative study of Hades 2 (heavy meta-progression) against The Binding of Isaac (minimal meta-progression) found the heavy-progression design sustains short-term motivation but "conceals the player's mastery," while the minimal design produces a slower but more legibly earned sense of achievement [verified: https://www.essays.se/essay/6d9ac81240/]. This is the roguelite compromise made concrete: softening permadeath with a meta-currency ledger keeps players returning after a loss, but every currency unit spent lowering the skill floor is a currency unit that can substitute for — and therefore obscure — actual improvement.
- **Corpse-run griefing / hostile-invasion spirals.** Dark Souls' asynchronous PvP lets other players invade a world specifically while the host is vulnerable (e.g., recovering a bloodstain), and the community had to develop unwritten etiquette norms to manage a design that offers no built-in fairness guarantee during that window [verified: https://dl.digra.org/index.php/dl/article/download/2271/2268/2286]. The failure mode is structural, not incidental: any design that puts a real, forfeitable stake at a fixed, telegraphed location (the death marker) creates an attack surface for a second party to exploit that stake's vulnerability window, independent of the victim's original mistake.
- **Hollowing has no bounded reclaim.** Unlike the souls bloodstain (one attempt, then gone), Hollowing accumulates with every death while cursed and is not spent back down by any action except a deliberate, costly cure — it is a pure accumulating tax with no run-scoped forgiveness window, illustrating that not every death-cost in a well-designed system needs (or gets) a reclaim mechanic [verified: https://darksouls3.wiki.fextralife.com/Hollowing].

## What the Swarm Analogue Requires

- [inferred] Two disjoint state classes must exist by design, not by convention: **run-bound state** (disposable, permadeath-eligible, equivalent to Obols/Boons/uncollected souls) and **meta-state** (survives run death unconditionally, equivalent to Darkness/Gemstones/character level/lit bonfires). No single piece of state should be ambiguous between the two classes at write time.
- [inferred] The mapping intuition supplied — agent session = run (disposable, permadeath by design); persistent correction/memory layer = meta-currency that must survive run death; procedural variation = each run's terrain differing — is directionally correct but needs one correction: Dark Souls shows a *third* thing that must survive run death alongside meta-currency — the floor of already-applied capability (level, gear) — which is not itself a "currency" and is never re-spent. The swarm analogue needs both an accruing meta-ledger AND a non-currency capability floor that a run cannot erase merely by failing.
- [inferred] What does NOT survive run death must be stated as plainly as what does: uncommitted in-run findings, exploratory dead ends, and any working state accrued after the last committed checkpoint are run-bound by default and should be treated as forfeit on session death, not silently retained as if they were meta-state.
- [inferred] The reward-class distinction must be visible to the agent *before* it commits effort to producing a given piece of output — the Hades door-symbol requirement. A swarm agent generating or discovering something mid-run should be able to tell, without inspecting implementation, whether that artifact is heading for the disposable run-bound bucket or the meta-persistent bucket.
- [inferred] Any reclaim mechanism for run-bound state that is granted must be **exactly one bounded attempt**, per Phoenix's report — this report adds only that the reclaim class and the meta-persistent class must never be conflated: a one-shot reclaim window is not the same guarantee as unconditional meta-persistence, and treating a recoverable-if-you-hurry item as if it were permanently safe is the exact failure Hollowing exists to punish (a cost with no reclaim, imposed for treating repeated risk as free).
- [inferred] The succession doctrine "inherit the lesson, not the obsession" is not merely a principle to apply to the swarm design — Hades and Slay the Spire/FTL already ship it as a mechanic: what persists across a run's death is never the specific solution-path or item build of that run (the "obsession"), only transferable capability — unlock pool breadth, permanent stat floor, procedural knowledge of mechanics (the "lesson"). A swarm's meta-persistence layer should be built to the same discipline: it should carry forward corrected capability and calibrated judgment, never a frozen copy of one run's specific context or conclusions.
- [inferred] Progression laundering is a named risk to design against directly: if the meta-persistence layer can lower the effective difficulty floor faster than the agent's actual judgment improves, evaluation of "is the swarm getting better" becomes causally ambiguous in the same way a heavily-meta-progressed roguelite makes player skill improvement ambiguous — the swarm needs some run-scoped, meta-progression-blind measure of raw capability to detect this.
- [inferred] Griefing/spiral surface: any state left at a fixed, telegraphed recovery point (Phoenix's bloodstain-equivalent) for a bounded reclaim window is a vulnerability window for a second actor (a concurrent process, a race condition, an adversarial input) exactly as an Elden Ring boss-arena or Souls invasion is — this should be named as an explicit risk, not assumed away because the swarm has no "other players."
