## Findings

### Incident A — `Running Copilot Code Review` failing 27/27 in-window, cause undetermined, NEW this cycle

Confirmed via direct job data (run `32506902249`, job `copilot-pull-request-reviewer`): step 19, "Processing Request (Linux)," fails after ~25 seconds; every other step in the job (checkout, MCP server setup, Copilot prep) succeeds. This is GitHub's managed Copilot code-review action (`dynamic/agents/copilot-pull-request-reviewer`, distinct from the separate `Copilot code review` app-installed workflow, id 247071622, which had no runs in-window) — not a file this repo owns or can patch. Sampled PR #999 (head commit `ade90adc`, one of the affected pushes) currently shows `mergeable_state: unstable`, not `blocked` — so this specific PR is not being held out of the merge queue by it, at least as sampled. But `VAULT-CONVENTIONS.md` § "Merge queue vs. auto-merge" names "the latest commit's Copilot review complete" as one of the PR-level **queue-entry** gates (`copilot_code_review`, `review_on_push`) — if this outage persists, it is a plausible path to a real entry-gate stall repo-wide, not just noise. **Not fixed here** — nothing in this repo to fix; flagged for Logan's awareness and for the next sweep to re-check. Later evidence, added on review (llamapreview, 2026-08-23): CI on this PR's own head showed an HTTP 402 monthly-quota error from the GitHub-hosted `copilot-pull-request-reviewer`, which points at account quota rather than a transient backend fault; the 402 came after this window, so it does not prove the in-window cause, and the cause stays undetermined. The "transient, will self-resolve" framing is withdrawn.

### Incident C — `Secret Pattern Policy` — 4 push-triggered failures; NOT self-resolved (corrected on review)

Originally reported as self-resolving flakes. GitHub Copilot's review challenged that on the specifics, and checking the actual job log (not just conclusions) confirms the challenge is right: run #4597 (2026-08-21T05:53:55Z, `claude/apply-patch-fixes-9gesn5`, attempt 1 on SHA `69652b6f`) failed with `fatal: bad object 2b7464a64826a458fa779c87a2a8d8c32cd4f710` — the pre-push `before` SHA was orphaned by a force-push — and the step exited 128 under `set -eo pipefail` before the actual secret scan ran on anything meaningful (the "secret-pattern guard: OK" line that follows is the scanner reporting clean on whatever the broken pipe handed it, not evidence the intended diff was scanned). The next run on that branch (#4600) succeeded on a *different* commit, not a retry of #4597 — it didn't hit an orphaned ref, it wasn't a fix taking effect.

I had attributed this to an already-landed fix, commit `02eb3213` ("fall back to merge-base when a force-push orphans `before`"), claiming it sat on the same branch as the failure. That was wrong: `02eb3213` was authored 2026-08-21T03:13:05Z on a *different* branch (`claude/rework-census-doctrine-463-4033po`, PR #820) and did not merge to `main` until 2026-08-25 — four days after this window, and unmerged at the time of run #4597. The bug was real and, as far as this branch's own history shows, still open at sweep time.

The other 3 failures in this incident (`claude/rework-census-doctrine-463-4033po`, `claude/shall-rome-lyrics-ok9049`, `wayback-audit-20260420100033`) were not individually re-verified against raw logs this pass — not claiming they're the same bug or that they self-resolved; they're unconfirmed.
