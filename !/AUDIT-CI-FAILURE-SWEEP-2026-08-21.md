## Findings

### Incident A — `_arm_auto_merge()` unhandled crash on "unstable status" — Code, **fixed in this PR**

Verified via direct job-log pull (job `96619333317`, run 32429932899, and independently on PR #1000's own `sync-pr` attempt at 2026-08-20T23:45:13Z): every time `review_feedback_loop.py sync-pr` runs against a PR whose checks haven't all resolved, `gh pr merge --auto` returns

```
! The merge strategy for main is set by the merge queue
GraphQL: Pull request Pull request is in unstable status (enablePullRequestAutoMerge)
```

and the script raises this as an unhandled `RuntimeError`, killing the whole job (`##[error]Process completed with exit code 1`). This is the largest single recurring failure signature found in the 48h window (dozens of occurrences across many PRs — the review-feedback-loop workflow runs on essentially every PR event). Fixed by adding `AUTO_MERGE_NOT_READY_FRAGMENTS` alongside the existing `AUTO_MERGE_AUTHZ_FRAGMENTS` handling: this specific message now returns `(False, "not yet ready to arm...")` instead of propagating, matching the function's own documented intent ("a not-yet-ready ... PR is expected to need another pass"). Added `test_arm_auto_merge_treats_unstable_status_as_not_ready_not_a_crash`.

### Incident B — root-level Python test suite silently uncollectable — Infra, **fixed in this PR**

All 9 `tests-test_*.py` files use a directory-depth-based loader (`Path(__file__).resolve().parents[1]`) to find the repo root and load the script under test via `importlib`. This arithmetic is only correct when the test file lives one directory below repo root (e.g. `tests/foo.py`); NETWEB path-flattening moved these files to sit directly at repo root (`tests-foo.py`), which needs `parents[0]`. Confirmed by direct reproduction against a simulated real GitHub Actions checkout path (`.../work/IDAHO-VAULT/IDAHO-VAULT/tests-test_review_feedback_loop.py`): `parents[1]` resolves to the checkout's *parent* directory, not the repo. Every one of the 9 files failed at module-import time with `FileNotFoundError` before this fix.

**No CI workflow currently runs any of these 9 files** (`grep -rl` across `.github/workflows/` for all 9 filenames returns nothing) — so this bug produced no red X anywhere; it just meant the suite has been dead weight, unable to verify anything, for as long as it's been in this state. Fixed the `parents[1]` → `parents[0]` arithmetic in all 9 files, plus one more gap specific to `tests-test_review_feedback_loop.py`: its loader didn't add `.github/scripts` to `sys.path` before `exec_module`, so `review_feedback_loop.py`'s own `from pr_threads import (...)` failed even after the path fix (the exact same gap `tests-test_stale_bot_prs.py` already handles correctly — copied that pattern over).

**What this does *not* fix:** with the infra bug cleared, the suite now actually *runs*, which surfaced pre-existing, previously-invisible test/implementation drift — not introduced by this PR, not touched by it:

- 4 of 9 files still fail to collect at all: `tests-test_five_wizards.py` (`idaho_vault.five_wizards` doesn't exist), `tests-test_sparkseed.py` (`idaho_vault.sparkseed` doesn't exist), `tests-test_runtime_doc_tools.py` and `tests-test_validate_bootstrap.py` (both look for a `scripts/` — not `.github/scripts/` — file that doesn't exist anywhere in the tree: `health_monitor.py`, `validate_bootstrap.py`). These reference modules that are not present in the repo at all; either deleted without deleting the test, or never actually committed.
- Of the 5 files that now collect and run: **11 of 24 tests pass**, 13 fail on genuine drift — mock targets renamed out from under the tests (`_resolve_outdated_advisory_threads` → `_resolve_outdated_resolvable_threads`; `review_feedback_loop._run` and `gh_cli._run` no longer exist under those names), and `assert_called_with` calls that don't match because the real `subprocess.run` calls gained kwargs (`timeout=`, `encoding=`, `check=`) the tests never picked up. `validate_content.py` no longer exports `validate_governed_metadata` at all — 4/4 of that file's tests fail on it.

None of this is a regression from this PR — it was unverifiable before this PR and unverifiable is not the same as passing. Flagged in full rather than partially patched, since picking off one or two of these individually risks leaving the record implying the rest are fine.

### Incident C — CodeQL Advanced failures: sub-agent's initial diagnosis was wrong, corrected here

A background sub-agent tasked with the initial 48h sweep reported CodeQL Advanced failing because "the repo has both GitHub's default CodeQL setup and this custom advanced workflow enabled simultaneously" — a real, common GitHub failure mode, but **not what the actual job log shows**, and not asserted as fact anywhere else in this document. Pulled job `96609491514` (run 32426525733, `Analyze (python)`) directly: the real cause is CodeQL's own Python parser failing on 5 vendored/third-party files under `.claude/plugins/marketplaces/.../skill-creator/scripts/*.py`, `.codex/skills/.system/*.py`, and `.ghcp-appmod/skills/java-knowledge-graph/scripts/*.py` — each logged as `A parse error occurred while processing <path>, and as a result this file could not be analyzed`, closing with `CodeQL job status was configuration error`. This is a scanning-scope question (should third-party plugin/skill payloads under `.claude/`, `.codex/`, `.ghcp-appmod/` be excluded from Python analysis, or are they genuinely malformed and worth a look upstream) — not a repo Settings toggle, and not something this sweep changes unilaterally. Flagged for Logan; not fixed here.

## Big IF

- **A test suite that has never run is not a passing test suite, and this vault's PR bodies have been asserting "tests pass" against exactly this suite for weeks.** Multiple prior sweeps and feature PRs (e.g. the NORMALIZATION PR, the topology-census word-boundary fix) cite specific pass counts (`341 passed`, `8/8`) — those numbers are almost certainly genuine local runs from a correctly-nested checkout at the time, not fabricated, but nothing has verified any of it in CI since the flatten. The gap between "an agent ran this locally and it passed" and "CI verifies this on every PR" is exactly the gap Restraint and Provenance exist to name rather than paper over. Wiring these 9 files into a CI workflow is a bigger, separate decision (blast radius: 13 currently-failing tests would need triage before the suite could gate merges) — flagged for Logan, not decided here.
- **The audit-PR pile shrank materially since 2026-08-19, but the pattern that grows it hasn't stopped.** #1002 (2026-08-19 sweep) is itself still open and unmerged two days later; this sweep does not add a third parallel report-only PR to that stack — it bundles with the two real fixes above, per the established "bundle with a fix, don't file report-only" instruction, and recommends merging #1000 and #1002 alongside this PR (numerically: #1000 first, then #1002, then this one) rather than leaving them to accumulate further.
- **Bot/App sprawl is still growing, independent of workflow-level CI health.** PR #1002's comment thread (16 comments) is entirely third-party marketplace bots — compliance-scan upsells, an unactivated design-review nag, a "no paid plan" skip notice, a ChatGPT-review bot missing its API key — zero from a human, zero substantive. This matches PR #984's 2026-08-18 finding of ~30 active review-bot Apps (up from ~15-20). Not a CI failure by GitHub's bookkeeping, but a legitimate signal for Logan about what's actually consuming attention on every PR opened in this repo.
- **A sub-agent's unverified claim almost made it into this record as fact (Incident C).** Caught only because this sweep pulled the actual job log before writing it down. Recorded here deliberately, not quietly swapped out, per the Repair axis — the corrected version is the only one that appears above, but the near-miss is worth naming as a standing reminder that a plausible-sounding root cause from pattern-matching is not the same as one read off a log.
